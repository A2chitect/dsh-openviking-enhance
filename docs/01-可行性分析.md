# 可行性分析

> 结论先行：**两个功能都可行，且不需要改动任何第三方代码。**
> 功能 1（Studio 面板）成本低、风险低；功能 2（commit 状态 + 影响记忆）数据源已实测打通，
> 但需要接受"轮询"而非"事件推送"的实现方式。
>
> 调研日期 2026-10-02；环境：DSH Desktop `0.2.0-rc.2`（build `5e9e301d`）、
> OpenViking `0.4.22`、`@openviking/dsh-memory-plugin` `0.5.11`、macOS / Node 22.22。

## 1. 功能 1：左侧边栏集成 OpenViking Studio

### 结论：可行 —— 纯 iframe 嵌入，零改造

| 问题 | 实测结果 |
| --- | --- |
| Studio 是否存在 | 存在。`GET http://127.0.0.1:1933/` → `302 → /studio/`，页面标题 `OpenViking Studio` |
| 谁提供 | **同一个 uvicorn 进程**。`openviking/server/app.py` 在 `web_studio/dist` 存在时挂载 `GET /studio` 与 `/studio/{path:path}`（SPA fallback） |
| 需要单独启动吗 | 不需要，也没有 `--studio` 参数；launchd 托管的服务起来就带着 |
| 能否被 iframe 嵌入 | 能。`/studio/`、`/health`、`/api/v1/*` 均**不带** `X-Frame-Options`，也无 CSP。全服务唯一带 `frame-ancestors 'none'` 的是 OAuth 同意页 |
| 跨域 | 无阻碍。CORS 中间件回显请求 origin（`http://127.0.0.1:19387` 实测通过），`allow-credentials: true` |
| 需要代理吗 | 不需要，而且**不应该**做代理：Studio 用相对路径 `/api/v1/...` 和 `localStorage`，一旦换到 DSH 的 origin 就会失效 |

### 界面挂载点（针对 DSH 0.2.0-rc.2 实测类型）

| 目的 | Slot | 类型 | 说明 |
| --- | --- | --- | --- |
| 左侧边栏新增一行 | `sidebar.panellist` | list / root | 注册项只画图标（`{size, active}`），按钮、标题、tooltip、高亮由 shell 负责 |
| 该行对应的主区页面 | `main`（keyed） | keyed / root | **key 必须等于 panellist 的 id**，否则点击会抛错 |
| （备选）左侧栏底部 | `sidebar.footer.action` | list / root | 收 `{wide}`，左下角动作位 |

内置的 Browser 页签（`ui-sidebar-browser`）**不能**用来打开 Studio：它的地址解析器
明确拒绝 DSH 自身 origin，但接受 loopback 的 HTTP 地址——所以 Studio 留在
`127.0.0.1:1933` 是可用的，而"把 Studio 代理到 DSH 端口再开"这条路是死的。

### 风险

| 风险 | 等级 | 处置 |
| --- | --- | --- |
| Studio 前端更新导致 iframe 布局变化 | 低 | iframe 自适应，无耦合 |
| OpenViking 版本升级移除 `/studio` | 低 | `/config` 路由会返回 `healthy:false` 并给出提示，面板降级为错误卡片 |
| DSH 升级改 slot 名 | 中 | slot 名写在 `src/client/index.tsx` 一处；`ctx.slots.inject` 会等待 slot 声明，缺失时只是不注册而不炸 GUI |

## 2. 功能 2：session 的 OpenViking commit 状态 + 影响记忆

### 结论：可行 —— 但必须从服务端取数，而不是从 DSH 插件取

#### 2.1 commit 是怎么触发的（已核对源码）

`@openviking/dsh-memory-plugin` 只有三条提交路径：

| 路径 | 触发 | 阈值 |
| --- | --- | --- |
| `runtime.mjs:193` `maybeCommit()` | `session/event` 且 `event.type === 'turn/end'` | 服务端 `pending_tokens ≥ commitTokenThreshold`（默认 **20000**） |
| `runtime.mjs:226` `dispose()` | agent fiber 卸载（会话/进程结束） | 无条件 |
| `pending-queue.mjs:423` | 断线重连后的队列重放（60s 定时） | 重放原请求 |

> 注意：`commitTurnThreshold`(8) 与 `autoCommitOnCompact` 在共享 schema 里声明了，
> 但在 DSH 插件里**从未被引用**，属于死配置。真正的判据只有 token 阈值 + dispose。

#### 2.2 为什么不能从 DSH 侧拿数据

| 想拿的东西 | 现实 |
| --- | --- |
| commit 是否发生 | 插件只 `logger.debug()` 记录，而 `dsh-app-boot` 的 exporter 级别是 2，`debug`(3) 被过滤——落不到任何日志文件 |
| commit 结果（task_id / archive_uri） | `maybeCommit` 只保留 `response.ok` 和 `trace_id`，**其余丢弃** |
| 服务的 commit 状态 | `ctx.provide("openvikingMemory", runtime)` 提供的是普通对象，无 commit 字段、无 emitter、无 `@Remote` |
| MCP | 15 个工具（`read/search/remember/...`），**没有任何 commit / diff / 历史工具** |

结论：功能 2 的数据只能从 OpenViking 服务端取；这也顺带让本插件对
`@openviking/dsh-memory-plugin` 的升级免疫。

#### 2.3 数据源（全部实测）

**(a) 提交状态** —— `GET /api/v1/sessions/{dsh-<sessionId>}`

```json
{"commit_count":1,"last_commit_at":"2026-09-30T13:32:06.618Z",
 "memories_extracted":{"total":8,"memory_write":4,"memory_edit":4},
 "pending_tokens":0,"keep_recent_count":10}
```

**(b) 某次 commit 影响了哪些记忆** —— 这是曾经的最大未知数，已解决：

```
GET /api/v1/fs/ls?uri=viking://user/default/sessions/<sid>/history
  → archive_001, archive_002, …      （第 N 次提交 = 第 N 个 archive）

GET /api/v1/content/read?uri=…/archive_00N/memory_diff.json
  → { "operations": {
        "adds":    [{"uri":…,"memory_type":…,"after":…}],
        "updates": [{"uri":…,"memory_type":…,"before":…,"after":…}],
        "deletes": [{"uri":…,"memory_type":…,"deleted_content":…}] },
      "summary": {"total_adds":1,"total_updates":2,"total_deletes":0} }
```

实测读到真实数据：`dsh-session-6b60b7d7…` 的 `archive_001` → **1 新增 / 2 更新**，
URI 精确到具体记忆文件。复现命令见 `04-调研证据.md`。

**(c) 提交进行中** —— commit 是两阶段的：`POST /commit` 先归档并返回 `task_id`，
记忆抽取在后台跑。此时 `archive_00N/` 目录存在但 `memory_diff.json` 返回 404。
这正好是 UI 需要的"抽取中"状态判据。

#### 2.4 关键坑位（已写进实现）

| 坑 | 处置 |
| --- | --- |
| `content/read` 的 `result` 是**字符串**，JSON 要解析两次 | `parseMaybeDoubleEncoded()` 循环解析至多 3 层 |
| `memories_extracted` 会**少算**：抽取任务失败时操作仍写入 diff，但计数不增 | UI 的条数一律取 `memory_diff.json` 的 `summary`，不取计数器 |
| `/api/v1/tasks` 记录会被**清理**（9-30 的提交任务已查不到） | 历史以 archive 目录为准，task 只用于标注进行中的提交 |
| 会话有 peer 作用域（git 仓库工作区按 git 身份派生 peer） | 从 `openvikingMemory.states` 读 `config.peerId` 并带 `X-OpenViking-Actor-Peer`；读不到时降级为不带 |
| 身份头 | 必须带 `X-OpenViking-User`（`fitbot` 等其它 user 的会话在 default 身份下读出来是空的） |

### 风险

| 风险 | 等级 | 处置 |
| --- | --- | --- |
| `runtime.states` 是**未文档化的公开字段** | 中 | 只用于"更好"，全部有降级：sessionId 回退 `dsh-<id>`、peer 回退空、阈值回退 `null`；HTTP 路径不依赖它 |
| OpenViking 升级改 `memory_diff.json` 结构 | 中 | 解析层集中在 `normalizeDiff()`，字段缺失时降级为计数 |
| 5s 轮询带来的开销 | 低 | 实测单次 session 详情 ~1KB/7ms，`fs/ls` ~0.5KB/8ms，diff ~24KB/4ms；并有 2.5s 服务端缓存 |
| commit 与 UI 不同步（无推送） | 低 | 轮询间隔 5s；`/commits` 同时给出 task 状态用于"抽取中" |

## 3. 平台能力可行性（实现侧）

| 需要的能力 | 结论 |
| --- | --- |
| 一个包同时提供 host 与 browser 两半 | 可行：`exports["."]` + `exports["./client"]` + `dsh.client.platform = "web"`，一条 patch 行同时挂载 |
| host → client 通信 | 用 `ctx.webServer.register(route)` + 前端**相对路径** fetch（两个在用的第三方插件都是这条路，无需 codegen）。Typert Remote 可选但需要严格 codec，收益不划算 |
| 客户端 bundle 格式 | 必须是预构建的懒 CJS：`window.__ModuleLoader__.load({id, factory})`，React 等平台模块走 shell 注入的 `require`，**不能打包进去** |
| 面板里放 iframe | 可行：内置 Browser 页签与 `dsh-better-sidebar` 都这么做；Studio 需要的 `allow-same-origin` 语义在不受限的 iframe 里天然满足 |
| 插件挂掉会不会拖垮 GUI | **会**——`apply()` 抛错会让整个 web shell 启动失败。因此两侧都做了 try/catch + `ctx.effect` 托管 disposer |

## 4. 总体结论

| 项 | 判定 |
| --- | --- |
| 功能 1 Studio 面板 | ✅ 可行，低成本，无阻塞 |
| 功能 2 commit 状态 | ✅ 可行，数据源已实测 |
| 功能 2 影响记忆明细 | ✅ 可行，`memory_diff.json` 给出精确 URI 与前后内容 |
| 是否需要 fork / patch 第三方插件 | ❌ 不需要 |
| 是否需要给 OpenViking 提需求 | ❌ 不需要（唯一遗憾是没有"按会话列 commit 历史"的官方接口，用 archive 目录替代） |
| 主要剩余不确定性 | 客户端 UI 尚未在真实 GUI 里挂载验证（slot 名来自 0.2.0-rc.2 类型声明 + 两个已发布插件的构建产物，未观测运行中的 slot 树） |
